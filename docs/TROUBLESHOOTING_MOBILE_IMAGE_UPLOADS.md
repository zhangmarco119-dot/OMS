# StoreHub 移动端图片上传排障与统一实现规范

## 适用范围

本规范适用于 StoreHub 中所有需要拍照、从相册选择、即时预览、保存、删除和全屏查看图片的功能。后续新增图片上传功能时，必须优先复用本规范中的结构和现有实现，不应重新设计另一套上传状态模型。

当前可作为基准参考的实现：

- 到货图片：`ArrivalImageSection`、`useArrivalDraft`、`arrival-images.service`；
- 任务执行图片：`V2TaskExecutionPage`、`TaskImagePreview`、`v2-tasks.service`；
- 模板参考图片：`TaskTemplateReferenceImageUpload`、`AdminTaskTemplatesPage`、`task-templates.service`。
- SOP 制作图片和产品预览图：`SopImageUpload`、`TaskTemplateReferenceImageUpload`、`AdminContentPage`、`v2-content.service`。

SOP 新建页没有业务对象 ID，因此首次选择图片时先保存完整 SOP 草稿取得 ID，再按本规范完成压缩、Storage、元数据和签名地址链路。多选图片必须串行处理草稿保存和步骤序号，上传成功后直接把服务端返回记录合并到页面状态，不整页刷新。

SOP 图片元数据必须通过 `asset_kind` 区分用途：`step` 是员工端连续显示的制作步骤，`cover` 只用于管理员列表的产品预览，`attachment` 是 PDF 附件。产品图上传成功后立即替换页面中的旧产品图；未设置产品图时，列表预览自动回退到排序后的最后一个 `step`，但不能把产品图混入员工制作步骤。

## 已解决的典型故障

移动端从相册返回后曾出现以下连续故障：

1. 页面显示“正在加载账号和门店信息”；
2. 模板编辑器被卸载并重新挂载，滚动位置跳回顶部；
3. 本地缩略图和 `File` 对象随组件卸载而丢失；
4. 图片可能已经进入 Storage，但数据库图片路径尚未关联；
5. 恢复出的旧浏览器草稿再次保存时，把服务器已有图片路径覆盖为空；
6. 发布后的任务快照不含参考图，员工和管理员审核页面都无法查看。

根因不是单一的“预览刷新不及时”，而是认证刷新、组件生命周期、两阶段上传和旧草稿覆盖共同形成的链路问题。

## 标准上传流程

### 1. 选择后立即建立本地预览

- 文件输入的 `change` 事件中立即调用 `URL.createObjectURL(file)`；
- 先把本地预览加入 `pending` 或临时图片状态，再开始压缩和网络请求；
- 上传完成前显示缩略图、进度和“正在上传”；
- 上传失败时保留本地缩略图，并提供明确错误和重试/移除入口；
- 成功或主动移除后调用 `URL.revokeObjectURL`，组件卸载时也要统一清理。

不要等 Storage、数据库或签名地址全部完成后才显示图片。

### 2. 保持受保护页面挂载

手机打开相机或相册时，浏览器会暂停页面。恢复后 Supabase 可能再次触发 `SIGNED_IN` 或 `TOKEN_REFRESHED`。

- 同一用户已经完成账号和门店加载时，只更新新的 session/token；
- 不要把认证状态重新切换为全屏 `loading`；
- 不要因此卸载受保护路由、文件输入、编辑器或上传队列；
- 只有首次进入、切换用户或确实缺少资料时才显示全屏认证加载页。

这是防止“相册返回后页面跳走、上传事件丢失”的关键规则。

### 3. 使用稳定的图片身份和分层状态

- Storage 路径使用业务对象 ID、项目 ID 和随机 UUID 组成；
- React 列表 `key` 使用稳定的数据库 ID 或 Storage 路径，不使用数组序号；
- 本地临时图片使用带 `local-` 前缀的独立 ID；
- 待上传图片和已保存图片分开管理；
- 上传成功后，用数据库返回记录替换对应临时记录，不整页刷新。

### 4. 压缩、Storage 和数据库必须形成完整链路

推荐顺序：

1. 校验文件类型和原始大小；
2. 在浏览器中压缩并限制最大边长；
3. 上传私有 Storage bucket；
4. 写入图片元数据或通过受保护 RPC 关联业务记录；
5. 生成短期签名地址；
6. 用正式记录替换本地临时记录。

如果第 4 步失败，应尽力删除刚上传的 Storage 对象，避免孤儿文件。上传服务返回成功前，必须确认数据库关联已经成功。

### 5. 服务器状态优先，防止旧草稿覆盖

模板参考图片上传和删除都会立即更新服务器图片路径。再次保存整个模板时：

- 已存在的模板项目以服务器图片路径为准；
- 本地草稿只负责普通字段和尚未创建到服务器的新项目；
- 不允许恢复出的旧草稿把服务器已有图片数组覆盖为空；
- 删除图片必须立即写服务器，不能只删除本地数组后等待下一次整表保存。

### 6. 上传中的提交校验

- 页面维护正在执行的上传 Promise 集合；
- 提交前等待所有上传 Promise 完成；
- 上传成功后立即更新图片列表和“已上传项目 ID”集合；
- 必传图片校验同时读取最新图片状态和成功上传集合；
- 删除最后一张图片时同步移除该项目的成功标记，下一次提交应重新提示上传。

不要要求用户刷新页面才能通过图片必填校验。

### 7. 删除图片

- 只允许任务仍可编辑且图片由当前账号上传时删除；
- 删除前弹出中文确认；
- 先删除数据库记录，再清理 Storage 对象；
- 数据库删除成功后立即从界面和校验集合移除；
- Storage 清理失败不能让已删除的数据库图片重新出现在界面，应提示后台后续清理；
- 已提交、已审核或无编辑权限的页面不显示删除入口。

### 8. 预览与滚动位置

- 缩略图点击后在当前页面使用全屏遮罩查看；
- 再次点击图片、遮罩或关闭按钮均可返回；
- 上传和删除过程中不导航、不刷新整页、不切换顶层 loading；
- 保持编辑器和列表稳定挂载，即可自然保留用户原来的滚动位置。

## 禁止使用的做法

- 上传完成后通过整页刷新获取图片；
- 只依赖下一次查询才更新本地图片列表；
- 同一用户 token 刷新时卸载整个受保护路由；
- Storage 上传和数据库关联之间没有失败补偿；
- 使用旧浏览器草稿无条件覆盖服务器图片路径；
- 仅在内存里删除图片路径、不立即同步服务器；
- 必传校验只读取首次加载时的图片数组；
- 以数组索引作为图片身份。

## 回归检查清单

每个新增或修改的图片模块至少验证：

- 选择图片后无需刷新立即显示缩略图；
- 从手机相机/相册返回不会跳到认证加载页；
- 页面保持原滚动位置；
- 上传中有进度或明确状态；
- 上传成功后立即替换为正式预览；
- 连续上传多张不会相互覆盖；
- 上传失败能够看到错误并重试；
- 保存、退出再进入后图片仍存在；
- 发布后的员工页面和管理员页面均能读取图片；
- 点击缩略图可全屏，再次点击可关闭；
- 删除图片后立即消失并可重新上传；
- 删除最后一张必传图片后，提交校验会重新阻止提交；
- 类型检查、lint、单元测试和生产构建全部通过。
